您已经读过 CSDM 5，并对其有了大致了解。然而，仍有许多悬而未决的问题和需要做出的选择。本文介绍我所推荐的实践，说明在 ServiceNow 中应该（以及不应该）建模哪些内容。采纳这些建议可以避免日后出现问题。

## 应在 ServiceNow 中存储的内容：

### 在数字产品组合（基线）中：

-   所有作为服务正式提供给公司的数字服务（Digital Services），包括基础设施、应用程序和 AI 数字资产（不分版本）。
-   业务部门直接使用的业务应用（Business Applications）（不分版本）
-   支撑业务的 IT 组件与平台（分版本）
-   产品模型（Product Models），例如用于硬件/软件资产的产品模型（不分版本）

### 在 CMDB（配置管理数据库）中（分版本的实例）：

-   公司自有（或由公司管理）的基础设施
-   在公司基础设施上部署/配置的项
-   部署在他方基础设施上的公司自有项
-   已连接的终端用户设备，包括其中/其上安装的内容。
-   产品/服务实例的所有（需付费的）许可证。

## 不应在 ServiceNow 中存储的内容：

-   由他方提供的服务的分解/组件，例如移动电信运营商的 GSM 天线。
-   作为外部 SaaS/PaaS 产品组成部分的基础设施。
-   作为业务应用的 MS SharePoint 站点、MS Teams 频道、Confluence 站点、文件共享等
-   未向公司提供/交付的组合项，例如公司与制造商、供应商或托管服务提供商之间没有正式协议的项
-   并非由公司的责任代表拥有/采购的组合项和 CMDB 项，例如 yahoo.com
-   其事件、问题、变更和请求管理由公司以外的他方在别处进行的 CMDB 项。
-   在公司总账中维护的财务属性（例如账面价值、折旧等）
-   在受支持的 ServiceNow 实践中不需要的项
-   公司当前明确排除在外的所有内容，例如本地部署服务器、电力设备和 OT 设备，包括其中/其上运行的内容。

* * *

**ServiceNow 作为企业服务管理平台**

ServiceNow 是一个面向企业级服务管理的平台。*服务*是平台中最重要的工件。如果不引用所提供的服务，就无法确定适用于事件、问题或变更的结果或承诺。只有已正式化的服务——最好是记录在公司与提供方之间的正式协议中——才应录入 ServiceNow。

如果公司希望衡量服务提供商的绩效、登记其所依赖的服务、为所有未决问题维护单一可信数据源，或利用其 AI 能力对事件、问题或变更进行评估和分类，就必须登记由提供商提供的服务。相关记录（例如事件和变更）可以通过电子邮件或 API 与供应商的服务管理系统自动实现 e-bonding（电子对接）。

* * *

**应用组合与基线**

企业架构师（EA）和应用组合管理者（APM）关注的是由业务使用、为业务服务的*应用基线*。他们管理这些基线的生命周期，包括横向依赖关系（接口）和纵向依赖关系（技术栈）。他们并不管理或跟踪这些基线实例的部署情况，但确实希望了解应用部署在何处以及其实际依赖关系。

只有将会污染业务应用组合或属于不同治理模型的工件排除在外，业务应用组合才能保持可管理。例如，如果将 Notepad++ 登记为业务应用，就意味着需要对其访问实施 RBAC、进行 BIA/CIA 评级并制定生命周期计划——而这一切仅仅是为了一个实用工具。由于一台典型的 PC 或 Mac 上可能装有数百个此类桌面应用，EA 和 APM 将不堪重负，被迫管理那些并非真正业务应用的项。桌面和移动应用通常通过应用商店或终端管理工具部署，不经过变更控制。

**建议：**不要将桌面或移动应用纳入业务应用组合。如果某项内容对业务至关重要，就不应将其部署在 PC 或移动设备上。

* * *

**版本管理与发现**

为避免数量呈指数级增长，应用*基线*在组合中不分版本。一个基线可以有多个已部署实例，每个实例的版本各不相同。这些版本通常通过自动发现和联合（federation）获得——无需人工投入。每个实例同一时间只能运行一个版本。

如果 APM 在 ServiceNow 之外进行管理，可以将实例版本计数从 ServiceNow 推送到 SAP LeanIX 或 Apptio 等工具中。如果基线分版本，那么每次升级时都需要重新关联所有实例，而除非应用及其数据被彻底替换，否则这毫无必要。例如，从 SAP R/3 迁移到云端的 SAP S/4HANA，就有理由创建一个新的基线。

* * *

**CMDB 与资产管理**

已部署的桌面和移动应用实例可以被发现并联合到 CMDB 中。经过关联和规范化处理后，它们可为资产管理、安全运营和风险管理提供支持。终端用户设备上已安装和正在运行的组件会显示在*设备表单*（Device Form）上。*设备*和*服务产品*（service offering）均与事件直接关联。虽然您*可以*引用已安装/正在运行的项，但最佳实践是将*设备*登记为受影响的 CI。

不由用户直接使用的基础设施软件、配置设置、中间件和技术工具**不应**登记为业务应用。它们的生命周期不由 APM 管理，其访问也不受 RBAC 管控。对基础设施的变更——例如为操作系统或 DBMS 平台打补丁——会影响多个业务应用，其处理方式与针对单个业务应用的变更不同。替换 EOL（生命周期终止）组件通常涉及大规模的基础设施项目。发现和联合有助于确认此类项的版本和位置。

在 LeanIX 中，IT 组件通常按主版本号进行版本管理（例如 *MS SQL Server 2016*）。在 ServiceNow 中，它们一般被记录为不分版本的*服务产品*（例如作为*数据库管理*服务一部分的 *MS SQL Server 支持*）。

* * *

**外部基础设施与风险考量**

如果业务应用（或其数据/组件）部署在第三方基础设施上，风险和审计相关方会希望对此有所掌握。建议通过内部服务管理解决方案来跟踪和审批涉及公司自有应用的部署和变更。

如果已部署的项需要付费，公司应主动监控其使用情况和利用率。如果许可证费用基于安装数量以外的使用指标，也应对这些指标进行监控。

提供黑盒服务的提供商很少公开详细的内部组件数据。只要提供商能够保证可用性、性能和安全性，这是可以接受的。公司可以要求提供合规证据，而无需将提供商的内部数据存储在公司的 CMDB 中——从而避免维护敏感的外部信息。

在没有正式协议的情况下登记由第三方提供的项是有风险的。提供商没有义务为公司提供支持、保持合规或确保连续性。审计人员和风险官很可能会认定这不合规。

如果公司依赖他方提供的服务，这些服务*必须*在公司的 ServiceNow 系统中体现。如果这些提供商在自己的 ITSM 工具中管理其事件、问题或变更，则不应在公司的 CMDB 中重复登记其内部组件——除非在严格治理下进行联合，并关注安全、GDPR 及合规方面的影响。

* * *

**在 ServiceNow 中管理范围与性能**

在 ServiceNow 中塞入不必要的细节（例如用户设备上的文件级数据）会降低系统性能。只应登记与 ServiceNow 或其相关方所支持的实践有关的项。

CMDB 的建设是一个持续多年的过程，应仔细规划并确定优先级。首先关注关键项。如果部分业务即将出售，该领域的发现工作可以降低优先级。临时性基础设施（例如临时备份虚拟机）除非被持续使用，否则不应登记。已停用的资源应及时退役。应记录并定期审查服务、资产和配置的范围及计划。

* * *

**现代协作平台及其分类**

SharePoint 站点、Confluence 空间、Google Workspace 和 MS Teams 频道等项通常不通过事件或变更流程进行管理。因此，不应将其归类为业务应用。而应：

-   将 “SharePoint”、“Confluence” 和 “MS Teams” 登记为业务应用。
-   通过从 O365 或 Atlassian 等平台进行联合，将 URL 自动登记为*应用服务*（Application Services）。
-   保持一致的分类和命名标准。

注意：一些审计人员可能会对将此类平台用于关键任务用途表示担忧。

* * *

**O365 与协作客户端**

终端用户设备上的邮件和协作客户端（例如 Outlook、Teams 客户端）应与其他桌面或移动应用一样进行登记。事件应针对*设备*提出，而非针对已安装的客户端。

一些公司将关键的 O365 组件登记为业务应用，并适用相同的治理策略。然而，O365 租户和应用通常是集中维护的，与标准业务应用有所不同。

**建议：**将 *O365 套件*登记为一个业务应用。将*企业邮件*、*协作*和*内容管理*定义为基础设施服务或服务产品。

* * *

**SDLC 组件与基线**

SDLC 组件（未列于所引用的表格中）要么在 ServiceNow 中登记为分版本的基线，要么完全不登记。两种做法各有利弊（参见其他博客）。若进行登记，这些组件将分版本管理并可被部署。其实例可在各类基础设施或云环境中被发现或联合。
