对于 ServiceNow 通用服务数据模型（Common Service Data Model，CSDM），业界有数以百计的不同解读。本文将介绍 CSDM5 在 ServiceNow 中是如何理解和实施的。

视角不同，关注点也不同。

-   项目集/项目经理管理**项目/需求组合（Project/Demand Portfolio）。**
-   企业架构师管理**应用组合（Application Portfolio）**
-   Product owner 在**产品组合（Product Portfolio）**中管理其组件的待办事项（backlog）
-   服务负责人（Service Owner）在**服务组合（Service Portfolio）**中管理其工件
-   配置经理在**配置管理数据库**（CMDB）中跟踪其 IT 资产清单
-   资产经理跟踪其****财务资产（Financial Assets）****的账面价值、运营成本、所在位置以及所有者/使用者。
-   主数据管理员（Master Data Steward）在各类工具中管理**基础性的跨组合数据**。

**ServiceNow 将所有这些组合都视为企业数字产品组合（Digital Product Portfolio）的一部分**，并通过数字组合管理（Digital Portfolio Management，DPM）对其进行管理。尽管如此，在 DPM 的底层，实际使用的仍是各个独立的组合、特定的实践和应用模块**。** 也就是说，如果不在 ServiceNow 中实施服务组合（及其管理），就无法在 ServiceNow 中开展 IT 服务管理。

> 如今，受管的组合条目由各自的干系人（在各个组合中）手工维护，而构建好的组件（存储在特定技术的存储库中）则通过自动化流水线进行部署。已部署的条目会被自动发现并记录到 CMDB 中，相关的资产（Asset）也会被自动创建/更新。已部署的条目还可以打上技术标签，使非技术性的属性值也能被自动识别，从而不再需要手工更新 CMDB。

十年前许多公司所采用的理念，如今已不再适用，例如：

-   IT 运营管理（ITOM）的**自动发现与联合（Automated Discovery and Federation）**已取代手工配置管理流程
-   需要定期确认和审查的应用/产品/服务数据被纳入各个组合，并通过**数字组合管理**实践进行管理。
-   资产（包括其状态、所有者、使用者、成本和所在位置）通过硬件/软件/云**资产管理**进行管理。
-   **敏捷 DevOps** 已取代/改变了 ITIL 变更管理和问题管理的部分内容。
-   **安全运营（Security Operations）**（针对生产及非生产条目）对企业而言已变得至关重要。
-   企业越来越需要遵守相关法规，例如有关**数据隐私、风险与合规**的法规（针对非生产及生产条目）
-   **云计算**已成为标准。云服务由 DevOps 工具通过 API 请求，并自动完成供应。
-   **人工智能**正在颠覆人们管理、治理和使用 IT 的方式。

CSDM5 中定义了以下工件：

-   **业务应用（Business Application）**是提供**业务能力（Business Capability）**的粗粒度产品，需要对其生命周期、授权使用和路线图进行管理。  
    一个业务应用在组合中只存在一次，但可以有多个产品实例，这些实例被建模为单独的服务实例（Service Instance）。  
    
-   **组件（Component）**是属于某个应用的细粒度产品，通过 DevOps 实践进行开发和维护。
-   **服务（Service）**由提供方提供、由使用方使用，可以与应用或其他产品相关联。  
    **业务服务（Business Service）**直接支持业务成果，对业务部门或最终用户可见。  
    **技术管理服务（Technical Management Service）**归 IT 部门所有，为一个或多个业务服务提供支持，但对业务部门不直接可见。
-   **服务产品（Service Offering）**是服务的变体（例如针对不同区域/时区，或区分生产/非生产等），每个服务产品都有各自的承诺，和/或由不同团队负责。
-   **服务实例（Service Instance）**是在一个或多个服务产品下获得支持、并与某个产品或应用相关联的已部署条目，例如一个网站、一个 API 等。
-   **服务交付系统（Service Delivery System）**是一组经单独发现/关联的配置项（Configuration Item），服务实例可能依赖于这些配置项。
-   **资产（Asset）**是已采购或已部署的单个条目的财务记录，这些条目列入公司总账，和/或可能需要为其支付许可费用。资产属于某个资产模型（Asset Model）。例如，在某台 PC 上发现的 NotePad++ 实例，就是"Notepad++"软件资产模型下的一项资产。

**说明：**

-   在 CSDM5 中，**业务应用仅限于直接支持业务成果、且对业务部门或最终用户可见的应用**。对于组合中的每个应用，都必须编制 CIA/BIA 评估并定期审查。此外，还需要为每个应用定义角色，并通过身份与访问管理（Identity and Access Management）将角色分配给具体用户。
-   对于企业所使用的成千上万个 PC/移动端软件包模型而言，上述管理/治理开销是不合理的，因此这些**软件包（模型）不被视为应用**。取而代之的是，由软件资产管理（Software Asset Management）跟踪软件资产，包括其在用实例数量。
-   **有些公司选择将所有技术工具、中间件、DBMS 及其他系统软件都登记为业务应用**。然而，这些应用并不直接支持业务成果，而且往往对业务部门或最终用户不可见。如果能够接受相应的管理/治理开销，并且这些技术应用遵循与业务应用相同的策略，那么这种做法也是可以接受的。另一种做法是，将技术应用登记到组合中，但豁免其适用于业务应用的治理要求。
-   以"即服务"方式提供的应用，如果其生命周期由公司管理，并遵循与其他应用相同的策略，则可以登记为业务应用。**如果某个解决方案以服务形式使用，但其生命周期由供应商管理，那么该解决方案被视为服务，而不是应用。**
-   **Azure、OCI、AWS 和 GCP 等公有云平台是以服务形式使用的**，其技术平台的路线图和生命周期由提供方管理。此类平台被视为服务，而非应用。
-   **公司可以在其以服务形式使用的平台上开发/维护自己的应用**。例如，SAP S/4 HANA 是以服务形式从 SAP 获取的，而公司（或其合作伙伴）在其之上创建定制配置/工作流。由公司（或其合作伙伴）开发的粗粒度应用可以登记为应用，其配置/脚本/API 则被视为组件。
-   鉴于唯一不变的就是变化，建议**采用市场标准的分类体系（taxonomy）和主数据**，其来源应具有权威性，最好与供应商无关，并由治理机构持续更新。例如，TBM Council 维护着一套优秀的分类模型，提供定义清晰、可直接使用的数据。

**特此说明****：**

-   ISO-27000、ISO55000、IFRS/GAAP 及其他正式框架中对**资产**的定义/范围界定与 ITSM/ITIL 中有所不同。
-   ServiceNow 区分**服务实例**（由使用方使用）和**配置项**（可支持一个或多个服务实例）。

-   对于服务实例，可以登记其与基础数据（Foundational Data）的关系。而配置项不应由人员在 ServiceNow 中手工改动
-   人员可以针对其有权使用的服务产品所关联的服务实例提交事件/问题/变更，但不一定能针对配置项提交。

-   **CSDM 既需要涵盖生产条目的信息，也需要涵盖非生产条目的信息**。不过，提供方针对这两类环境的服务产品和承诺可能不同，而且某些实践（例如变更管理）仅适用于生产环境的服务产品。
-   每家 IT4IT 供应商都为其平台使用各自的术语和定义。考虑到一项企业实践应只在一个全企业范围的平台上实施，**使用供应商特定的术语/定义（例如与该平台相匹配的最佳实践流程指南、视频教程、社区文章）是合理的**。**采用源自过时和/或不兼容框架的定义/术语则毫无意义。**

-   **业务应用：** "SAP S/4 Hana Platform"、"SAP ERP Application"、"SAP CALM Application"、"ServiceNow Platform"、ServiceNow ITSM/ITOM/ITAM"、"Workday"。
-   **技术应用：** "Intune"、"JAMF"、"Cisco Works"、"SQL Server 2016"、"SQL Server 2022"、".NET 4"、"Python 7"、"MuleSoft"、"Tibco"  
    
-   **组件：** "SN MidServer"、"JAVASCRPT X V93.47"、"AI Agent Y"

**各要素分别用在哪里？**

事件管理、变更管理和问题管理等 ITSM 流程会引用以下内容：

-   受事件、变更或问题影响的**服务实例**
-   **服务产品**，包括适用于该服务实例（及其他类似服务实例）的承诺和订阅
-   **服务**，即该服务产品所属的服务（也就是服务产品的父项）
-   **服务交付系统（又称** **配置项/资产）**，它们为服务实例提供支持，并直接分配给用户（例如用户的 PC/手机）。  
    
-   提供方的**分派组（Assignment Group）**和**被分派的处理人员（Assigned Agent）**，负责完成变更、事件或问题的处理。
-   受变更、事件或问题影响的**使用方**（包括公司、地点等相关数据）。

其他非 ITSM 实践同样对 CSDM 有所要求，即使这些实践未必在 ServiceNow 中实施：

-   **企业架构师**需要了解其组合工件仍有多少实例在部署/使用中。
-   **SecOps** 需要掌握所有环境（而不仅仅是生产环境）中的漏洞信息。
-   **DevOps** 需要能够确定已部署组件的所在位置和版本。
-   **项目**需要了解有哪些已部署的 API、微服务、AI Agent 等可供使用。
-   **过渡经理（Transition Manager）**需要了解需要过渡的现状/数量。
-   **财务资产经理**需要了解哪些资产/许可证被谁使用，和/或哪些因不再使用而可以回收。
-   **身份与访问管理人员**需要了解哪些条目（不再）可以申请/授权访问。
-   **风险经理**需要了解所发现的配置是否符合策略和经授权的基线。
-   **人工智能**需要了解 IT 基础设施中的相关条目，包括其相互依赖关系，以及谁可能将其用于何种用途。
-   **HR 经理和直线经理**需要了解为其员工分配了哪些角色、资产和身份。
-   **终端用户设备经理**需要了解各个使用年限/版本的设备仍有多少在用。
-   **服务交付经理**需要了解他们从合作伙伴处使用了哪些服务。
