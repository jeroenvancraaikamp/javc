Das Common Service Data Model von ServiceNow ist derzeit ein heißes Thema in der Welt des IT-Managements. Ich kenne einige Leute, die tatsächlich versucht haben, das CSDM-Whitepaper zu lesen; es gibt sogar ein CSDM-Training bzw. eine CSDM-Zertifizierung. Das breit angelegte, abstrakte CSDM5 nach dem Prinzip „One size fits all“ bietet ein Datenmodell, das neben den vielen Frameworks bestehen kann, die Sie möglicherweise in Ihrem Unternehmen einsetzen.

Ähnlich wie IT4IT 3.0 unterscheidet das CSDM die Domänen „Ideation & Strategy“, „Design & Planning“, „Build and Integration“, „Service Delivery“, „Service Consumption“ und „Manage Portfolio“. Jedes Objekt im Datenmodell gehört genau einer Domäne an. Derzeit nutzen nur wenige Unternehmen eine einzige Plattform zur Verwaltung aller Domänen. In der Regel erfolgt „Build and Integration“ mit mehreren technologiespezifischen Tools. Observability, Continuous Integration, Continuous Delivery und Container-Orchestrierung werden zunehmend als eigenständige DevOps-Domänen behandelt. Auch Security Response wird zunehmend zu einer eigenen Domäne.

In der obigen Abbildung sind die wichtigsten Objekte des Common Service Data Model (CSDM) aufgeführt, unabhängig davon, in welcher Domäne sie laut ServiceNow genutzt bzw. verwaltet werden. Dadurch ist die Abbildung universeller einsetzbar, unabhängig davon, ob (Varianten von) DevOps, Dev & Ops, DevSecOps, BusDev oder BusDevOps verwendet werden.

### CSDM-OBJEKTE

CSDM definiert das Objekt **Business Application**, das ein (logisches oder physisches) Produkt oder ein Service sein kann und null oder mehr Business Capabilities/Funktionalitäten ermöglicht. Eine Anwendung kann null- oder mehrmals bereitgestellt werden. Eine Anwendung kann Komponenten enthalten, die unabhängig oder als Teil der Anwendung bereitgestellt werden können. Jede Business Application hat einen Lebenszyklus, der von einem agilen Team verwaltet werden muss. Andere Frameworks verwenden für Business Applications den Begriff „Solution“, meinen aber genau dasselbe. Im CSDM gilt auch als Service bereitgestellte Anwendungssoftware (SaaS) als Business Application.

Middleware, Cloud und IaC gelten nicht als Business Applications, sondern als Technology Management Service Offerings. Die bereitgestellten technischen Elemente werden als Teil eines Infrastruktur-Stacks bzw. -Templates bereitgestellt,

Application Stacks von bzw. für Business Applications und/oder Technology Management Services können mehrfach instanziiert werden. Jeder bereitgestellte Stack wird als **Service Instance** bezeichnet. Typischerweise sind Stacks umgebungs-, technologie- oder standortspezifisch oder eine Kombination daraus. Beispiel: Ein Unternehmen hat drei länderspezifische O365-Produktions-Tenants und einen generischen O365-Test-Tenant. Insgesamt verfügt das Unternehmen damit über vier Service Instances derselben „AD Application“. Manche Service Instances sind keine Stacks, sondern logische Gruppierungen gleichartiger Elemente (z. B. „Windows Servers in NL“ und/oder „Windows Production Servers“.

Ein Stack ist typischerweise eine Sammlung zusammengehöriger Elemente, z. B. eine Java Application Resource, die auf einem Java App Server gehostet wird, der auf einem Windows Server läuft usw. Jedes Element wird separat als Configuration Item (CI) registriert. Die Gesamtheit der CIs wird als **Service Delivery System** (früher als CMDB bekannt) bezeichnet**.** Die Elemente sind über CI-Relationen miteinander verknüpft. Manuelle Registrierung gehört heutzutage der Vergangenheit an; die Elemente und ihre Beziehungen werden automatisch erkannt (Discovery) oder aus einer vertrauenswürdigen Datenquelle föderiert. Die Service Instances werden (manuell oder automatisch) mit den übergeordneten CIs verknüpft, von denen sie abhängen.

> Die Configuration Items in der CMDB werden in klassenspezifischen Tabellen gespeichert. ServiceNow umfasst über 800 hierarchische CMDB-Tabellen (z. B. erweitert die Tabelle „Windows Server“ die Tabelle „Server“, die die Tabelle „Computer“ erweitert, die die Tabelle „Hardware“ erweitert, die wiederum die Tabelle „Configuration Item“ erweitert). Die (Groß-)Elterntabellen enthalten die Datensätze ihrer (Enkel-)Kindtabellen. Die Kindtabelle erbt die Attributdefinitionen von ihrer (Groß-)Elterntabelle. Dennoch gehört jedes CMDB-Objekt genau einer Klasse an. Zwei CMDB-Objekte können über zulässige Beziehungen eines definierten Typs miteinander verknüpft sein (z. B. Server X „contains::contained by“ Disk Y)
> 
> Statt Benutzer Datensätze in einer der 800 Tabellen auswählen zu lassen, empfiehlt es sich, ihnen alle Datensätze aus einem Dutzend übergeordneter (Ur-)Elterntabellen anzuzeigen, z. B. „Application Resources“, „Web Resources“, „Database Resources“, „MSSFT Database Servers“, „IIS Webserver“, „Windows/Linux Servers/VMs“, „Hypervisors“, „usw.“

Interne und externe Kunden können **Business Service Offerings** in Anspruch nehmen. Der **Business Service** definiert, was bereitgestellt wird, und das Business Service Offering definiert konkrete Varianten davon. Jedes Offering wird von einem Team bereitgestellt bzw. unterstützt. Derselbe Service kann in zwei Ländern unterschiedliche Öffnungszeiten und Support-Zusagen haben und von unterschiedlichen Support-Teams betreut werden. Für manche Services gibt es ein Standard-Offering und ein erweitertes Offering. Ein Business Service Offering kann von standort-, organisations- oder unternehmensspezifischen Personengruppen abonniert werden. Ein Business Service Offering kann von null oder mehr Service Instances abhängen. Business Service Offerings, die für interne Kunden/Mitarbeitende bestimmt sind (z. B. „HR Payroll“ oder „Zeiterfassung“), sollten nur von internen Unternehmen abonniert werden.

Jede zugrunde liegende Technologie, die ein Unternehmen nutzt, muss von einem internen oder externen Service Provider bereitgestellt werden. Die Technologie wird entweder als Service bereitgestellt oder als Service verwaltet. Der Service wird von der Partei in Anspruch genommen, die die Service Instance besitzt bzw. verwaltet, welche von dieser zugrunde liegenden Technologie abhängt. **Technology Management Service Offerings** definieren Zusagen, Abonnements und Governance für die zugehörigen Service Instances. Beispiel: Ein Provider stellt ein Technology Management Service Offering „Windows Server Support“ bereit, das Teil des **Technology Management Service** „Hosting Support“ ist. Wenn Sie unterschiedliche Teams einsetzen, z. B. um Benutzer in einer bestimmten Region zu unterstützen, empfiehlt es sich, standortspezifische Offerings anzulegen und die Benutzer in diesen Regionen diese abonnieren zu lassen. Wenn Sie zwischen Produktions- und Nicht-Produktionsservern unterscheiden möchten, können Sie für beide separate Offerings anlegen. Falls nötig, können Sie auch kombinierte regionen- und umgebungsspezifische Offerings anlegen. Wenn Sie drei Instanzen derselben Anwendung haben, die jeweils von einer bestimmten Benutzergruppe genutzt werden, müssen Sie separate Service Instances anlegen und KÖNNEN separate Service Offerings und Abonnements anlegen. Tipp: Legen Sie keine separaten Offerings an, wenn Zusagen, Abonnenten und Support-Teams (nahezu) identisch sind.

### BEST PRACTICES

-   Business Applications sollten versionsunabhängig sein. Das heißt: Legen Sie keine separaten Business Applications (z. B. ServiceNow, Zurich) für jede Version der Anwendung an, wenn sich nur die Version unterscheidet und die übrigen Attribute gleich sind.
-   PC-Anwendungen werden als Product Models von auf PCs erkannten Softwarepaketen registriert, nicht als Business Applications. Einzelne Instanzen von PC-Anwendungen werden nicht als Service Instance registriert. Auch wenn ich es nicht empfehle, können Sie einen TASK oder einen CASE mit einem End-user Device Service Offering verknüpfen und auf das darauf installierte Software-CI verweisen.
-   Geschäftskunden/Mitarbeitende sollten Technology Management Services weder in Anspruch nehmen (noch darauf verweisen) können.
-   Für jede Business Application muss es mindestens ein Service Offering mit mindestens einer Service Instance geben,  
    damit Events und Vulnerabilities auf einer Service Instance dieser Anwendung dem Team zugewiesen werden können, das das Offering bereitstellt, welches die Service Instance enthält.
-   Wird eine Business Application dem Business als Service angeboten, muss dieser Service als Business Service oder als dessen Business Service Offering registriert werden.  
    Idealerweise sollten Business Services und/oder Business Service Offerings jedoch geschäftsorientiert (z. B. „Payroll“) und nicht technologieorientiert (z. B. „Workday“) sein.

### NUTZUNG VON CSDM-DATEN

In ServiceNow-Instanzen, die CSDM nutzen, gibt es eine klare Trennung zwischen Technologie und Business. Die beiden Welten sind grundsätzlich voneinander getrennt, aber eng miteinander gekoppelt.

Business-Anwender oder externe Kunden können Cases/Issues/Calls/Requests zu den Service Offerings erstellen, die sie abonniert haben. Dies geschieht über das Employee-/Customer-Portal oder – zunehmend – über einen KI-gestützten Chatbot. Der Chatbot weiß, wer der Anfragende ist, was er abonniert hat und welche Anliegen das Business oder andere Mitarbeitende zuvor gemeldet haben, einschließlich der jeweiligen Lösungen. Kann der Chatbot den Case nicht lösen, kann dieser dem Helpdesk zugewiesen oder mit einem bereits eröffneten technischen Incident verknüpft werden.

Jedes Service Offering hat eigene Zusagen und einen eigenen Kreis von Abonnenten. So können Personen in Belgien einen Case bei HR Belgien erstellen, in der Regel aber nicht bei HR Niederlande. Dadurch werden sie nicht durch Offerings abgelenkt, die für sie nicht relevant sind. Zudem ermöglicht dies ein datengesteuertes Routing von HR-Cases, die von Benutzern in den Niederlanden erstellt werden, an das HR-Team, das für die Niederlande zuständig ist. Ebenso können Anliegen zu PCs in einem Gebäude an den Helpdesk für dieses Gebäude geleitet werden. Gemeldete Probleme/Fragen zu O365 können an einen lokalen Helpdesk weitergeleitet werden, bevor ein Incident dem zentralen 2nd Level zugewiesen wird.

Anliegen von Kunden/Mitarbeitenden müssen mit einem abonnierten Business Service Offering verknüpft sein und können mit der betroffenen Service Instance verknüpft werden, von der das Service Offering abhängt. Beispiel: Service Offering „Payroll“ des Service „HR“ und Service Instance „Workday \[PR\]“. Bei manchen Business Service Offerings kann ein passendes CI ausgewählt werden, das dem Anfragenden zugeordnet ist. Meldet ein Anfragender beispielsweise ein Problem mit einem „Windows Computer“, kann sein Laptop/VDI als betroffenes CI identifiziert werden.

Beobachtete Events, Vulnerabilities, Alerts und gemeldete Service-Beeinträchtigungen können bearbeitet werden, indem dem technischen Support-Team, das dem betroffenen Technical Management Service Offering zugeordnet ist, ein Task zugewiesen wird. Durch das Design lässt sich automatisch ermitteln, welches Offering die betroffene Service Instance enthält und welches Team einbezogen werden sollte. Falls relevant, kann automatisch ein Case erstellt werden, über den die betroffenen Mitarbeitenden/Kunden informiert und auf dem Laufenden gehalten werden können. Umgekehrt kann ein KI-Agent die Erstellung eines 2nd-Level-Incidents auslösen, wenn offensichtlich ist, dass der 1st Level den Incident nicht lösen kann.

Teams können Incidents, Requests und andere Tasks auf ihre **agilen Task Boards** ziehen und sie dort zuweisen, kommentieren oder lösen. Wiederkehrende Incidents können als Defects eingestuft und anschließend über agile Stories bearbeitet werden. Angeforderte kleine Erweiterungen können über Stories umgesetzt werden.

TASKS wie Incidents, Changes, Stories usw. müssen mit einem abonnierten Technical Management Service Offering verknüpft sein und können (optional) mit den betroffenen Configuration Items und/oder Service Instances verknüpft werden. Tasks können Mitgliedern der entsprechenden Teams zugewiesen werden, die im Technology Management Service Offering hinterlegt sind.

Zunehmend entstehen TASKS aus DevSecOps-Events bzw. -Agenten. So kann Rapid7 beispielsweise eine Vulnerability auf einem Configuration Item erkennen und einen Vulnerability-Response-TASK-Datensatz erstellen. Das CI ist einer Service Instance zugeordnet, die in einem Technical Management Service Offering enthalten ist, das einem Team gehört bzw. von ihm verwaltet wird. Anhand der CSDM-Daten können die relevanten Teams automatisch ermittelt und über erkannte Vulnerabilities benachrichtigt werden.

Für alle, die es nicht wissen: TASKS ersetzen keine CASES und umgekehrt. Sie bestehen nebeneinander, erfüllen jeweils ihren eigenen Zweck und haben eigene Kommunikationswege. Ein Case kann zu vielen Tasks führen, und ein Task kann mit vielen Cases verknüpft sein. Wird ein Case aktualisiert, können die zugehörigen Tasks aktualisiert werden und umgekehrt. Wird ein Task geschlossen, können die zugehörigen Cases geschlossen werden (oder auch nicht). Work Notes zu Tasks sind für Personen, die nicht zur Einsicht in den Task berechtigt sind, nicht sichtbar.

Kunden-CASES müssen die SLA-Zusagen einhalten, die für das Business Service Offering gelten.  
Der technische TASK muss die OLA-/UC-Zusagen einhalten, die für das Technical Service Offering gelten.

Durch Anpassen der Abonnements der Offerings lassen sich alte Offerings nahtlos und gezielt durch neue ersetzen.  
Ändern sich Zuständigkeiten, können die zuzuweisenden Gruppen in den Service Offerings geändert werden.

### SCHLUSSBEMERKUNGEN

Mit CSDM lässt sich ein BUSiness-, DEVelopment-, SECurity- und OPerationS-Ökosystem schaffen, in dem (nur) relevante Daten denjenigen zur Verfügung stehen, die sie kennen müssen. Die Objekte aktualisieren sich gegenseitig, wenn bzw. sobald dies erforderlich ist.
