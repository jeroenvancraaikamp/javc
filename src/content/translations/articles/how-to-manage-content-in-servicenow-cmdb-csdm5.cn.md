填充并维护一个准确的配置管理数据库（CMDB），并使其与 ServiceNow 的通用服务数据模型（Common Service Data Model，CSDM）保持一致，对大多数企业而言都是一项重大挑战。本指南阐述了如何正确做到这一点、哪些类型的项应当（以及不应当）登记在 CMDB 中，以及实现高质量数据的最有效方法——既适用于当今的技术，也为未来的需求做好准备。  

### 核心理念

  
企业应手动定义并维护其组合基线（例如服务、服务产品、应用）。这些基线的实例——即 CMDB 的内容——应从授权数据源自动发现或联合（federate）获取。**任何人都不应手动更改 CMDB 配置项（CI）的属性或关系，以确保 CMDB 反映技术现实。** 在不影响自动化数据质量的情况下，可允许有限的例外。

企业只应登记其自有的项/关系，以及企业从内部或外部提供方（以服务形式）消费的项。服务提供方应（在其自己的 CMDB 中）跟踪其以服务形式提供的内容；管理企业产品实例的 MSP（托管服务提供商）必须将这些实例发现/联合到企业的 CMDB 中，以便企业始终能够基于自己的 CMDB 对其自有资产进行报告。  

### **引言**

  
ServiceNow 提供多种方式来填充/更新 ServiceNow CMDB 中的配置项（实例）。  

  
-   **ServiceNow 提供五种方法（可并行使用）来识别 ServiceNow CMDB 所需的配置项（CI）。**  
    
      
    -   通过 IP 扫描（IP sweep），可以发现已知/可见 IP 地址段中的所有 IP 设备（所有设备的 IP/MAC 地址、FQDN 以及可用的管理协议，如 SSH、WMI、RDP 和 SNMP，均可获知）
      
    -   安装在 Linux/Windows/MacOS 设备上的 Agent Client Collector（ACC）可以向 ServiceNow 报告其所在设备的信息。
      
    -   通过联合（Federation），ServiceNow 可以（从各种数据源）获取这些数据源有权提供的配置项。
      
    -   当 ServiceNow 通过集成收到某个 CI 的事件时，可以（在需要时）将该 CI 登记到 CMDB 中。
      
    -   授权用户可以通过导入文件或直接通过 ServiceNow GUI，在 ServiceNow 的 CMDB 中手动登记 CI（及其关系/属性）。
      
    
      
    
  
-   **ServiceNow 提供五种方法（可并行使用）来发现和联合获取已检测到的 IP 设备上安装/运行的内容。**  
    
      
    -   如果已配置相应的权限/凭据，可以使用基于凭据的发现（ServiceNow 登录到 IP 设备）
      
    -   可以使用无凭据发现，通过查询已检测到的 IP 设备的可用管理协议来实现（ServiceNow 将获取可访问的信息）
      
    -   Agent Client Collector（ACC）可以向 ServiceNow 报告其所在设备上运行/存在的绝大部分内容，以及谁在何时正在/曾经使用该设备。
      
    -   通过联合，ServiceNow 可以（从各种数据源）获取已知配置项中/上运行内容的信息。
      
    -   授权用户可以通过导入文件或直接通过 ServiceNow GUI，在 ServiceNow 的 CMDB 中手动登记 CI 中/上安装的内容。
      
    
      
    
  
-   **ServiceNow 有三种方式来确定 CMDB 中已登记技术栈（及其中的项）之间的依赖关系**  
    
      
    -   通过基于凭据的发现，ServiceNow 可以识别模式和依赖关系（例如，此应用组件消费了那个应用的这个数据库/API）
      
    -   通过联合，ServiceNow 可以（从各种数据源）获取依赖关系（例如，根据 APM，此应用与那个应用之间存在接口）
      
    -   授权用户可以手动登记 CI 的已知依赖关系
      
    
      
    
  
-   **ServiceNow 自动化可以（前提是企业已采购相应许可）**  
    
      
    -   对已安装 Agent Client Collector 的 IP 设备上（未）运行/安装/配置的内容提供细粒度洞察
      
    -   为服务台提供对已安装 Agent Client Collector 的 IP 设备的远程访问
      
    -   在已安装 Agent Client Collector 的 IP 设备上安装/卸载软件，或修改软件设置/策略。
      
    -   直接接收来自已安装 Agent Client Collector 的 IP 设备的已配置事件/告警。
      
    -   使用 ServiceNow Integration Hub 安装/移除云服务/资源（例如用于云优化）
      
    -   使用 ServiceNow Integration Hub 安装/移除 IAM 服务/资源（直接在 AD/Entra 中，或通过 SailPoint/Saviynt）
      
    -   直接或通过 ServiceNow MID Server 触发 AI 代理和脚本
      
    
      
    
  

  
供参考：ServiceNow 中还包含组合项（基线）（及其属性/关系）：  

  
-   业务应用和业务能力使用 ServiceNow 中的 APM 模块（SPM 的一部分）进行维护，或在其他授权数据源（LeanIX、Apptio 等）中维护。
  
-   服务、服务产品（Service Offering）及其承诺/权益使用 ServiceNow 中的 DPM 模块进行维护。
  
-   SDLC 组件在 DevOps 模块中采用 Agile/SAFe 实践进行维护
  
-   可订购的产品目录项使用服务目录管理（ITSM 的一部分）进行维护
  
-   资产/CI 模型和许可在 ServiceNow 中使用软件/硬件资产管理进行维护，或作为已发现/联合的 CI 信息的一部分提供。
  
-   集成风险管理、业务连续性管理和安全运营各自拥有/管理其基线工件，这些工件通常与 CMDB 中的实例相关联。
  
-   基础主数据（例如公司、业务单元、部门、国家、地区/省份、语言、货币、地点、组、用户、角色等）可以在 ServiceNow 中维护，  
    但它们通常由 ServiceNow 从其他授权数据源获取（例如 Workday、HCM、SuccessFactors、AD、Saviynt、SailPoint、ISO 3166、IANA 等）
  

  
*本文其余部分重点介绍通过 ITOM/ITSM 在 CMDB 中登记和维护实例 CI。*  

### **考虑因素**：

  

  
-   CMDB 内容正变得越来越细粒度，并且必须近乎实时地保持更新。
  
-   公有云平台、网络/网元管理器、SD-WAN、AI 和 CDaaS 工具现在都能向 ServiceNow 提供 CMDB 信息，通常使用开箱即用的集成/连接器。
  
-   一些平台拥有自己的数据源（例如 Copado、SAP CALM、SAP ChaRM、GitLab、SolarWinds 等），可以向 ServiceNow 提供 CMDB 信息，通常使用开箱即用的集成/连接器。
  
-   越来越多的企业选择零接触（Zero-touch）CMDB，除应用/服务组合基线外，无需手动维护任何 CMDB 内容。
  
-   一些企业允许在 CMDB 中手动维护某些类型/类别（没有合适数据源）的 CI/资产，例如汽车、自行车、设施、钥匙、机架、机笼。
  
-   ServiceNow 无法发现它"看不到"的内容，也无法发现不与 ServiceNow 联系（例如通过 ACC 或 API）的内容。
  
-   ServiceNow MID Server 可以将 ServiceNow 的可见范围扩展到连接在本地或第三方 IP 网络中的内容。
  
-   在高度复杂/隔离/安全的 IP 网络中，通常需要大量 MID Server 或 Agent Client Collector。
  
-   企业拥有的终端用户设备越来越多地在企业场所之外使用（例如居家办公人员），且并不总是连接到企业网络（例如通过 VPN）。
  
-   "自带"设备/许可（BYO）会影响传统的工作/登记方式。
  
-   一些企业（例如国防部门）使用本地安装的 ServiceNow 实例，这带来了特定的挑战和限制。
  
-   如果您还希望支持风险/合规管理、应用组合管理、供应商管理或资产管理，那么 CMDB 中需要的数据将超出 IT 服务管理所需的范围。
  

  

### **指导原则：**

  

  
-   遵循 ServiceNow 通用服务数据模型中的定义/关系。尽可能使用与 ServiceNow 的开箱即用（OOTB）集成。  
    仅在合理且已充分考虑长期影响的情况下才进行定制。
  
-   仅当自动化不可行，且能够确保对相应 CMDB 数据进行妥善维护和定期数据审查（认证）时，才手动维护 CMDB 内容。
  
-   如果 CMDB 中有一个或多个项/资产需要手动维护，外部审计人员将坚持要求对相关流程进行文档化/实施/培训/维护/治理，并针对这些项开展持续数据质量改进活动。
  
-   在采用包含 CI 实例（及其关系）的零接触 CMDB 时，企业需要维护所需的 CMDB 技术集成，并由组合/服务负责人通过数字组合管理（Digital Portfolio Management）手动维护组合基线。
  

  
**何时在 Windows/Linux/MacOS 计算机上安装/使用 Agent Client Collector（ACC）？**  

  
-   当企业无法轻易让 IP 设备对 ServiceNow 可见时（例如，IP 设备位于多道不允许开放的防火墙之后）
  
-   当企业希望了解 IP 设备上软件/资源的实际使用情况时（即用于软件资产管理）
  
-   当企业希望使用 Agent Client Collector 监控/管理 PC/VDI 等 IP 设备时（用于服务台/SecOps）
  
-   当企业没有/不使用 JAMF/Intune/SCCM 等能够将 PC 信息联合到 ServiceNow 的工具时
  
-   当企业需要 ACC 提供的、而 JAMF/Intune/SCCM 无法提供的信息时。
  

  
*供参考：就 ServiceNow 许可而言，CI 以何种方式进入 CMDB 并无影响；ACC 的使用已包含在 ITOM 许可价格中。*  

### **何时使用 ServiceNow MID Server？**

  

  
-   当企业希望对位于防火墙之后、未安装 Agent Client Collector 的 IP 设备执行 ServiceNow 发现时。
  
-   当企业希望管理/访问位于防火墙之后的 IP 设备（及其中/其上的内容）时（无论是否安装了 Agent Client Collector）
  
-   当企业希望 ServiceNow 访问无法从公共互联网直接访问的 API 时（例如 OCI API）
  
-   当企业对部分 IP 网络进行隔离，导致 ServiceNow 或其其他 MID Server 无法看到该网络中所连接的内容时。
  

  
*供参考 1：尽管 MID Server 软件不需要付费的 ServiceNow 许可，但安装该软件的虚拟机会产生操作系统许可、IAM 和维护方面的成本*

*供参考 2：MID Server 存在容量/性能限制。此外，不建议在同一台 MID Server 上混合承载生产与非生产流量。因此，您很可能需要多台 MID Server*  

### **在发现和自动化中使用凭据**

  
如果选择基于凭据的发现来填充/更新 CMDB 内容和/或安装/卸载软件/设置，ServiceNow 需要相应的凭据：  

  
-   可以将 ServiceNow 配置为使用（数量有限的）存储在 ServiceNow 本地的通用账户/密码组合（设置/维护简单，但通常不受 SecOps 青睐）
  
-   可以将 ServiceNow 配置为使用存储/维护在 CyberArk 中、不会存储在 ServiceNow 中的凭据（需要与 CyberArk 集成，但通常更受 SecOps 青睐）
  

  
*注：此处假设账户凭据已预先配置在需通过基于凭据的发现进行发现的 IP 设备上（例如作为镜像的一部分）  
基于凭据的发现所用账户需要对设备上的清单信息具有只读访问权限。*  

### **自带（BYO）设备**

  

  
-   BYO 设备归企业以外的另一方所有。它们是否应纳入您的 CMDB？
  
-   BYO 设备上安装的软件可能由另一方而非企业拥有/付费。
  
-   如果您希望在 CMDB 中登记 BYO 设备（例如用于 SecOps 或支持），请将该设备标记为 BYO。
  
-   对标记为 BYO 的设备（及其中/其上的内容）应用 BYO 规则。
  

  

### **SaaS/PaaS 解决方案**

  

  
-   配置项通常由内部/外部托管服务提供商"以服务形式"（作为单个单元或捆绑包）提供。其基线（即模型）不登记在 CMDB 中。  
    所提供服务的实例可以登记为"服务实例"（Service Instance），并与其所依赖的 CI 建立关系。
  
-   对于大多数第三方 SaaS 服务（作为托管黑盒提供），其 CI 是未知的，不会登记在 CMDB 中。  
    SaaS 服务/服务产品（基线）在数字组合管理中定义或通过其定义。如果提供了多个 SaaS 实例，可以将其登记为"服务实例"。
  
-   大多数主流 SaaS 提供商（例如 Microsoft、SAP、Salesforce、Google、Asana 等）都提供 API，企业可以借此了解哪些用户/角色消费了哪些许可/服务。
  
-   部分 SaaS 提供商提供允许用户申请或停用许可、服务或角色的 API。
  

  

### **标记与映射：**

  

  
-   现代配置项可以添加标签（tag）。不同的键（Key）用于不同的目的。标签作为 CI 的一部分提供给 ServiceNow  
    
      
    -   一些企业将 CI 的环境用作标签（例如开发、测试、生产）。
      
    -   需要与其所属服务产品（直接）建立关系的 CI，应使用该服务产品的唯一 ID 进行标记。  
        随后，该标签将用于创建"服务产品依赖于云服务账户"的关系/映射（即基于标签的映射）
      
    
      
    
  
-   对未加标签、但可能需要映射到服务产品的 CI 进行分组。  
    
      
    -   可以定义 CI 组，并将其成员手动映射到这些组（例如同一应用的 D、T、A 和 P 环境）。
      
    -   类别/类型相似的 CI 可以基于查询自动映射到组（例如"所有常驻阿姆斯特丹的用户的 Windows 10 PC"）
      
    
      
    
  

  

### **何时发现/联合 CMDB 数据？**

  
在理想情况下，CMDB 内容应近乎实时地更新。遗憾的是，目前的技术还不够理想。当前建议：  

  
-   每天获取所有联合 CI（属性/关系）的变更（即"增量加载"），最好在非办公时间进行。
  
-   每周获取所有活动联合 CI 的全部（属性/关系）（即"全量加载"），对目标（CMDB）进行完整的重新同步。
  
-   每天运行每个发现作业，例如每天对整个 IP 网络扫描一次。
  
-   将不同作业分散在一天中运行，以尽量减轻 ServiceNow 实例/MID Server 的负载。
  
-   如有需要，运行实时的临时发现（针对已安装 Agent Client Connector 的配置项）
  
-   如有可能，实时更新 CMDB 内容，例如由数据源将其数据推送到 CMDB 中。
  

  

### **如何管理 CMDB 健康状况？**

  

  
-   使用 Performance Analytics 或 BI 工具跟踪/审查量化趋势，例如：  
    
      
    -   上一周期末按类别、按数据源统计的活动项总数
      
    -   上一周期内按类别、按数据源统计的新建项数量
      
    -   上一周期内按类别、按数据源统计的更新项数量
      
    -   上一周期内按类别、按数据源统计的停用项数量
      
    
      
    
  
-   定义"良好"的标准并进行监控（和报告），例如：  
    
      
    -   安装了软件的计算机所占百分比（应为 100%，BYO/非托管设备除外）
      
    -   过去 90 天内已更新/提供的活动 CI 所占百分比（应为 100%）
      
    -   承载服务器虚拟化的虚拟机所占百分比（应高于 90%）
      
    -   应分配给在职人员的 CI（例如 PC、手机）中，实际已分配给在职人员的百分比（应高于 90%）
      
    -   位于已知地点的物理 CI 所占百分比（应为 100%）
      
    -   等等。
      
    
      
    
  
-   每月报告 CI/关系的覆盖率、完整性、准确性、陈旧度以及（可选的）合规百分比（及其趋势）
  
-   治理技术集成（与每个集成数据源的负责人定期审查数据和计划）
  
-   让手动维护的 CI/关系由其 CI/服务负责人进行认证。
  
-   在需要时开展数据质量改进项目。
  
-   跟踪哪些项是由事件管理工具创建的（为什么它们没有通过正常途径进入？）
  

  

### **典型大型企业的推荐方案：**

  
建议大型企业采用以下做法：  

  
-   **个人计算：**
  

  

  
-     
    
      
    -   从 JAMF 和/或 Intune（如有使用）联合获取个人设备（包括其中/其上安装的内容）
      
    -   如有必要，在个人计算机上安装 Agent Client Collector，例如用于补充来自 Intune/JAMF 的数据并实现远程 PC 管理。
      
    -   使用这些设备的全球供应商（例如 Dell、Lenovo 等）的开箱即用 API，从其处联合获取个人设备/支持信息
      
    -   针对 BYO 设备（及其中/其上的内容）的管理，确定按国家/技术区分的策略（不同国家 → 不同的法律法规和员工委员会）
      
    
      
    
  

  

  
-   **办公计算**
  

  

  
-     
    
      
    -   从办公打印机（服务）的供应商处联合获取这些打印机（服务）的信息。
      
    -   从设施资产管理工具联合获取设施资产（CCTV、电梯、OT 设备、LED 电视等）
      
    -   使用 SNMP 或自定义模式（Custom Pattern），发现通过 IP 控制器管理的相关 OT 设备（例如 PLC）。
      
    -   从 BAM 工具联合获取楼宇门禁管理数据（即生物识别读取器、闸机/门）
      
    
      
    
  

  

  
-   **云工件：**
  

  

  
-     
    
      
    -   使用开箱即用的 Service Graph Connector，将 AWS、Azure、GCP 中的云工件联合到 CMDB 中
      
    -   使用开箱即用的插件联合获取 OCI 中的云工件。使用基于凭据的发现或 Agent Client Collector 发现 Linux/Windows 服务器。
      
    -   如有需要：使用 ServiceNow Discovery 发现云容器中的内容及其相互依赖关系。
      
    
      
    
  

  

  
-   **本地设备（不包括个人计算）**
  

  

  
-     
    
      
    -   在企业 IP 网络中部署（生产与非生产分离的）MID Server
      
    -   如果安全部门允许：使用无凭据发现，发现连接到企业相关 IP 地址段的设备。
      
    -   如果安全部门不允许 IP 扫描：在 Windows/Linux 服务器上安装 Agent Client Collector，和/或从授权数据源（例如 SolarWinds、PRTG、SCCM）联合获取数据
      
    
      
    
  

  

  
-   **网络计算**
  

  

  
-     
    
      
    -   如果安全部门允许发现：使用无凭据发现，发现连接到企业相关 IP 地址段的路由器/交换机。
      
    -   如果安全部门不允许发现：从权威数据源（例如网络管理器、网元管理器）联合获取网络设备数据
      
    -   从权威数据源联合获取网络配置数据，如网段、防火墙规则、IP 地址段、VPN 和证书。
      
    
      
    
  

  

  
-   **SaaS/PaaS 解决方案**
  

  

  
-     
    
      
    -   从第三方采购的 SaaS/PaaS 服务（基线）必须手动登记为服务/服务产品。其实例/租户（CI）可以手动或通过发现登记为服务实例。
      
    -   如果企业希望通过 ServiceNow 可视化并管理 SaaS 许可/服务/角色，建议与相关 SaaS/PaaS 提供商（例如 Microsoft、SAP、Salesforce、Google）进行集成。
      
    
      
    
  

  

### **结语：**

  

  
-   对于某些企业，可能需要/更倾向于对上述建议进行调整。
  
-   并非所有数据源都具备相同的能力；细节决定成败。
  
-   ServiceNow 很出色，但并不完美；有些定制只是让它变得更好 :-)
  
-   请聘请 CMDB/CSDM 专家，针对贵企业的需求/能力，就最佳配置/路线图提供建议。
