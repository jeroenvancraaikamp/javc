您可能已经知道，ServiceNow 有一个可在整个 ServiceNow 平台中使用的通用服务数据模型（Common Service Data Model，CSDM）。CSDM 4.0 白皮书对每个对象（及其各自的用途）都作了说明。ServiceNow 文档中提供了示例，以便按预期方式使用 CSDM。然而，对大多数人来说，CSDM 的概念很难理解，因此，CSDM 对象中经常被填入本不应放在该对象中的内容。

CSDM 的内容是以下几类事物的混合：设计项（基线）、这些基线模型的各个版本，以及这些带版本的基线模型的已部署实例。一个事件（incident）会关联到一个或多个基线，以及被认为出现故障的那个项。例如，在 ServiceNow 中我们有“沃尔沃汽车”“沃尔沃 V70 汽车”“沃尔沃 V70 柴油汽车”等，这些都是基线。然后我们有一辆特定的沃尔沃 V70 柴油车，车牌号为 XX-AMS-99，这是一个实例。它装有一台 D5 柴油发动机（模型），序列号为 393092。在打补丁时，通常只针对单个实例打补丁。不过，也可以在一次变更中修复所有“沃尔沃 V70”汽车。但这并不意味着我们要在“沃尔沃 V70”这一基线上登记变化。

在自己 PC 上使用 Google Docs 的人，可能不明白为什么 Google Docs 的建模和处理方式与 Notepad++ 或记事本（Notepad）不同。例如，记事本是一款桌面应用程序，是 Windows 操作系统的组成部分。将记事本登记为业务应用（Business Application）、服务（Service）或服务产品（Service Offering）不被视为良好实践。Notepad++ 是一款桌面应用程序，可以像其他数百种桌面应用程序一样安装在 PC 上。这些桌面应用程序实例通常不受正式的 change management（变更管理）管控。更常见的情况是，这些应用程序实例通过 Intune 或类似工具自动打补丁。

设计人员和架构师可能希望把自己的每一个细粒度组件都建模为应用程序，却没有意识到最终用户在致电服务台时，往往并不知道是哪个部分出了故障。MS-SQL Server 或 JAVA Server 是需要打补丁和进行生命周期管理的许可软件包，但这并不意味着它们就是已部署的业务应用。

一个业务应用可能用于多种目的。大型企业拥有数十个业务应用、数百个可能被部署的软件包模型（Software Package Model），以及这些模型所支持的数千项功能。有些软件包包含多个组件。一个团队可能以相同的方式支持/处理多个应用程序（基线）。业务用户通常并不了解“引擎盖”下面有什么。他们往往希望 IT 保持简单。例如，他们通常只想说明自己无法再使用虚拟桌面服务了。至于是哪一个基础设施项上的哪个组件导致了故障，最终用户并不认为这有什么相关性。

过去，CMDB 中的内容需要手动登记、审计和更新。如果管理员记录的内容过多，通常就无法很好地维护，CMDB 中的数据过一段时间后就变得毫无用处。如今，CMDB 的内容主要是通过发现（discovery）获得，或者从受管数据源中收集（联合，federation）而来。人们可能会忍不住把所有发现/联合得到的内容都导入 CMDB。然而，凡是存储在 CMDB 中的内容，都必须有相关的用例。对某个人合适的内容，对另一个人可能并不合适。如果在 CMDB 中放入过多的项/属性，CMDB 就会变得缓慢而复杂；如果在 CMDB 中设置的项/属性过少，CMDB 虽然运行很快，但用途很可能十分有限。

并不是 IT 部门的每个人都是 CSDM 专家。IT 人员并不太热衷于行政管理工作；因此，他们有时会“忘记”充分登记自己（能够）提供的服务。结果，服务组合中可能会出现缺口。此外，未登记的内容就无法作为服务进行计费，只能以不透明的一次性年费形式收取。我们未登记的内容，也无法得到充分的保护/管理。

幸运的是，IT 技术是高度标准化的。CMDB 内容（配置项）是自动发现的，因此也越来越标准化。联合导入 CMDB 的内容可能存在污染，并有粒度或基数方面的问题。为 CMDB 自动发现的内容越多，CMDB 中的一致性和数据质量就越好。话虽如此，有时（目前还）无法发现所有内容。这时，联合可能就是您最好的替代方案。

应用程序和软件/硬件组合的管理只有一种方式，那就是正确的方式。首先，要定义受管对象、受管属性、允许的属性值、命名规范以及允许的关系。在组合中登记的每一个工件，都必须有合理的理由、一个负责的所有者，以及一个确保相关内容保持最新的人。组合的所有变更都必须经过负责的数据所有者批准。标准、规则和准则必须向所有使用或维护这些内容的人公开。数据质量必须受到监控、报告，并（在必要时）加以改进。

ServiceNow 支持登记服务层级结构。但 ServiceNow 并不附带市场标准的服务组合内容。大多数企业都未能很好地定义/维护自己的服务层级结构。企业自行构建的企业级服务模型往往不一致、不完整，或（部分）不适用。企业不应自行登记内容，而应为服务组合中的工件采用现有的市场标准名称和定义。

2014 年，TBM Council（一个由 700 名专家组成的开放论坛，类似于 IT4IT 的 Open Group）发布了一个市场标准数据模型的第一个版本，其中包括为技术业务管理（Technology Business Management，TBM）定义的内容。IT 行业中的 IT 架构师、财务规划人员和组合经理越来越多地使用 TBM 标准。TBM 模型与 ServiceNow 的 CSDM 模型是兼容的。TBM 内容中的对象名称可能与 CSDM 中的对象名称不同，但映射对象的意图往往是相同的。因此，TBM 内容可以一对一地加载到 ServiceNow 的 CSDM 模型中。

作为起点，将 TBM 解决方案（Solutions）映射到 ServiceNow 中最为合理。TBM 包含成本池（Cost Pools）、IT 塔（IT Towers）、解决方案（Solutions）和消费者（Consumers）（的定义和内容）。TBM 4.0 包含已定义的解决方案（类型、类别）。类型和类别是分层的分类节点（Taxonomy Nodes，也称占位符）。TBM 有 6 种类型，其中 3 种用于面向客户的解决方案，3 种用于 IT 内部使用的服务。用 ServiceNow 的术语来说，这些解决方案就是我们的服务。面向最终用户的服务被建模为业务服务（Business Service），IT4IT 服务则被建模为技术服务（Technical Service）。

建议保持 TBM 的类型、类别和解决方案不变，以最大程度地符合标准。TBM 提供了“Business”类型的一套标准类别和解决方案。TBM Council 针对某些行业推荐了已定义的业务解决方案。不属于特定行业的公司建议使用这套标准集。

TBM Council 还提供了挂在已定义的 TBM 解决方案（CSDM 服务）之下的服务产品（Service Offering）的代表性示例。建议以这些示例为起点，并在需要时、在需要的地方对服务产品进行更新。
